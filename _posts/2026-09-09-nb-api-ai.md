NocoBase 的 AI 能力（AI 员工、LLM 接入、知识库）平时都在设置界面里配，但排查「AI 员工为什么不回话」「LLM 服务到底存了什么」时，命令行看原始结构更直接。这篇记 `nb api ai` 的三个子主题：employees、llm-providers、llm-services。

## 命令用途

- `employees`：AI 员工的增删改查（每个员工本质上是一份带 prompt 与聊天配置的配置记录）
- `llm-providers`：发现可用的 provider / 模型，以及测试一份**尚未保存**的配置能否连通
- `llm-services`：已保存的 LLM 服务配置（provider + 模型 + apiKey 引用）

## 语法与常用参数

```bash
# 列出 AI 员工
nb api ai employees list

# LLM 服务
nb api ai llm-services list
nb api ai llm-services get --filter-by-tk <serviceKey>

# provider 与模型发现
nb api ai llm-providers list

# 保存一个 LLM 服务
nb api ai llm-services create \
  --values '{"name":"my-deepseek","provider":"deepseek","modelName":"deepseek-chat","apiKey":"{{$env.MY_KEY}}"}'
```

## 实测效果

`employees list` 返回的员工记录里，一个典型的「团队长」角色结构大致是（节选）：

```json
{
  "key": "atlas",
  "name": "atlas",
  "title": "Atlas",
  "defaultPrompt": "你是团队负责人，负责理解需求并分派给合适的成员...",
  "greeting": "你好，我是 Atlas...",
  "chatSettings": { "model": "...", "temperature": 0.7 }
}
```

`llm-services list` 里能看到已保存的服务，注意 apiKey 字段的样子：

```json
{
  "name": "deepseek-main",
  "provider": "deepseek",
  "status": "active",
  "options": { "model": "deepseek-chat" }
}
```

而真正的密钥在配置里是以 `{{$env.Opencode}}` 这样的**环境变量引用**形式存的——数据库里不落明文。

## 踩坑点

**1. apiKey 用 `{{$env.X}}` 引用环境变量。** 这是 NocoBase 的密钥托管机制：保存 LLM 服务时把 key 写成 `{{$env.变量名}}`，运行时由服务端解析到实际值。好处是配置可以导出、备份而不泄露密钥。代价是——如果目标环境没有定义这个变量，服务会静默变成「key 为空」，表现为调用时报鉴权失败但配置页看起来一切正常。排查时先确认环境变量存在。

**2. 不要把明文 key 写进 create 的 `--values` 里。** 虽然语法上允许，但那会进数据库和可能的备份文件。统一走 `{{$env.*}}`。

**3. llm-providers 的「测试」针对未保存配置。** 它的用途是在保存前验证 provider/模型/key 是否可用，和 `llm-services` 里已保存服务的连通性检查是两回事。

**4. 员工的 defaultPrompt 是完整 system prompt。** 想知道某个 AI 员工「为什么会那样回答」，直接 get 它的 defaultPrompt 看原文，比猜有效得多。

## 什么时候用

- 换模型供应商、换 key 时核对服务配置
- AI 员工行为不符合预期时，先读它的 defaultPrompt 与 chatSettings
- 多环境迁移前检查：所有服务是否都用了 `{{$env.*}}` 引用（有明文就先改掉再迁移）

一个实用习惯：把「检查所有 llm-services 是否引用环境变量」写进迁移前的 checklist，避免到新环境才发现密钥丢了。
