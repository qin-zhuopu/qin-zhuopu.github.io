权限排查是运维 NocoBase 绕不开的事：「这个角色到底能干什么？」「为什么这个用户看不到菜单？」`nb api acl` 把角色的策略、资源权限、桌面路由授权都搬到了命令行，写审计脚本或者快速核对都很方便。

## 命令用途

`nb api acl` 下的子主题：

- `roles`：角色的 list / get / create / update / destroy
- `available-actions`：系统当前可被授权的动作清单
- `data-sources`：按数据源维度的权限
- `desktop-routes`：桌面端菜单/路由授权
- `roles-resources-scopes`：角色-资源-范围（scope）的细粒度授权关系

## 语法与常用参数

```bash
# 列出所有角色
nb api acl roles list

# 看某角色的详细策略
nb api acl roles get --filter-by-tk admin

# 系统里可授权的动作有哪些
nb api acl available-actions list

# 数据源、资源权限关系
nb api acl data-sources list
nb api acl roles-resources-scopes list
```

## 实测效果

`roles list` 里 admin 角色的关键信息（节选）：

```json
{
  "name": "admin",
  "title": "Admin",
  "strategy": {
    "actions": ["create", "view", "update", "destroy", "export", "importXlsx"]
  },
  "allowNewMultiPortal": true,
  "snippets": ["pm.*"]
}
```

几个可以直接读出来的结论：

- admin 的 strategy 是「全局放行」这些动作，不需要逐资源配
- `allowNewMultiPortal: true` 表示该角色允许进入新建的多 Portal
- `snippets` 里的 `pm.*` 对应插件管理器的全部权限

`available-actions list` 返回的是一份动作字典——哪些 action 名字在授权界面里可选、分别挂在什么资源类型上。写自动审计脚本时，先拉这份清单做合法性校验，比硬编码 action 名稳妥。

## 踩坑点

**1. `desktop-routes list` 报 command not found。** 我实测的版本（2.4.0-alpha 系列）上执行 `nb api acl desktop-routes list` 直接提示该命令不存在，但 `desktop-routes` 这个 topic 在 `--help` 里是出现的。结论是：**ACL 子命令的名称随版本变化明显**，遇到「help 里有、执行没有」的情况，先 `nb api acl desktop-routes --help` 看看实际挂了哪些动作，必要时退回用 `nb api resource` 直接打 `desktopRoutes` 集合。

**2. 角色名是 filter-by-tk 的值。** 传的是 `admin` 这种 role name，不是 title。

**3. 只读审计也可能踩到版本差异。** 上面的 `strategy.actions` 结构在不同小版本里有增减字段，脚本里用 `.get()` / 默认值兜底，别假定字段一定在。

## 什么时候用

- 接手一个陌生实例，先 `roles list` + 逐角色 `get`，快速画出权限全景
- 上线前核对：新角色是否真的只放行了预期动作
- 排查「用户看不到某个菜单/页面」类问题——先看角色，再看 desktop-routes 授权，最后才怀疑前端缓存

权限问题的排查顺序建议是「角色策略 → 资源级授权 → 路由授权 → 缓存」，`nb api acl` 把前三步全部覆盖了，不用在 UI 里层层点进去。
